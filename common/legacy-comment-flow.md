## 评论模板

```
━━━ AI审核 · 深度审视 ━━━
📂 场景: [场景]
📋 申请资质: [类型]
🔗 审批链接: [applink]

【证据链核实】
  [✅/⚠️/❌] 平台截图/合同/律师函等
  → 结论：证据充分 / 证据不足

【逻辑穿透结果】
  ✅ 看流向：[结果+依据]
  ⚠️ 看用途：[结果+依据] / [缺失项]
  ❌ 看背景：[结果+依据] / [缺失项]
  ⚠️ 一问：[结果+依据] / [无法确认项]

【风险控制】
  替代：[建议]
  限制：[🔴红线检查结果 / ⚠️风险提醒]
  技术：💧 [≤15字水印建议]

【结论】
  [✅建议通过 / ❌建议退回 / ⚠️需补充]
  补充建议: [非必需的优化建议]
```

> 注：`fullAnalysis` 字段（`write-result` JSON schema）也采用此三阶段格式，两者内容规范一致。

---

## 结论判定标准

四档：✅通过 / ❌退回 / ⚠️需补充 / 🔴转人工 — 完整标准见 [analysis-protocol.md](analysis-protocol.md)。
> 核心：判断由你(大模型)做，工具不替你下结论；操作性细节不升级结论；审核评的是"公司该不该为这件事担责"。

## 写入评论（两种方式）

### A. 从审核报告文档提取（推荐，含缓存）

> 前提：已完成分析报告输出（格式见 references/examples.md「分析报告格式」节），将分析报告写入飞书云文档并取得 `doc_id`。若未写云文档，直接用方式 B。

**Step A-1（批量缓存，写评论前先跑一次）**：
```bash
# 一次拉取文档，提取全部 case 段落并缓存到磁盘
node scripts/audit-tool.cjs cache-from-doc <doc_id> \
  1:<instance_code_1> 2:<instance_code_2> ...
```
输出 `{ cached_cases: [1,2,...], instance_writes: [...] }`。此命令只拉一次文档（约 24K），所有 case 均从本次内容提取并缓存。

**Step A-2（逐条写入，读缓存，不再拉文档）**：
```bash
node scripts/audit-tool.cjs comment-from-doc <instance_code> <doc_id> <case_number>
```
缓存命中顺序：实例级(`comment_draft.txt`) → 文档级(`doc_<id>/case_N.txt`) → 回退到按需拉文档并缓存全部。`cache_source` 字段说明实际来源。

### B. 临时文件方式（备用）

把评论文本写入一个临时 `.txt`（UTF-8），然后：
```bash
node scripts/audit-tool.cjs comment <instance_code> <临时文件>
```

两种方式均处理编码/查重/限流：已有**今日** AI评论 → 自动跳过（视为最新分析）；有历史评论但无今日评论且不止一条 → 按附录A写「统一版」。审批链接用 `case` 返回的 `applink`。

> ⚠️ 写入时注意 `@file.json` 的 CWD：lark-cli 解析 `@filename` 相对于其进程 CWD（= Node.js 运行时的 CWD，通常是技能包根目录）。所有 params/body 文件必须写到与 CWD 一致的目录，否则"file not found"。

## 修正版（如需，原 SKILL.md 步骤 6）

**触发条件**：发现之前评论错误、附件读取能力修复后、"其它"类被错误跳过、资质类型识别错误。

**核心规则**：修正=完整重新审核，不是复述。必须：①说明修正原因 ②列出附件结果 ③重新分析 ④给出新结论。

> **历史降级（统一版）**：`comment` 返回 `needs_unified:true` 时 → 写统一版（完整三阶段重审，标题含"（统一版）"，说明冲突）。新流程已基本消除，仅兜底。（背景见 references/CHANGELOG.md）
