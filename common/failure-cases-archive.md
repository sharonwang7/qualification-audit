## P原则完整定义


### 【P2】读取表单全部字段 —— 注册号/品牌/平台等字段同等重要

**起源场景**：莫铭茵 — 没看到表单字段的注册号

| 项目 | 详情 |
|------|------|
| **错误** | 第一次分析说"缺注册号"，后来发现表单字段 `提供注册号` = "7629781" |
| **根因** | 只看了事由文本，没有读取表单完整字段 |
| **后果** | 前后评论矛盾， credibility受损 |
| **判断标准** | 注册号可能在独立字段中，不能只看事由。必须读取全部表单字段（注册号/品牌/平台/相对方）后再下结论。 |
| **修正方式** | 读取表单时，打印所有字段值，特别是注册号、品牌、平台、相对方四个字段必须显式读取。 |
| **融入规则** | SKILL.md 步骤2 |

### 【P3】附件是证据链的核心依据 —— 不能凭事由推测

**起源场景1**：李驰骋 — 国家电网入驻（漏读附件）

| 项目 | 详情 |
|------|------|
| **错误** | 有1个附件（53.6KB）但未读取，仅凭事由文本判断"缺注册号、'其它'不明" |
| **根因** | 分析疲劳——连续处理多条后，对"入驻"类申请产生路径依赖 |
| **后果** | 证据链判断基于推测而非证据 |
| **融入规则** | 所有品牌/商标/授权类资质，无论事由长短，强制读附件 |

**起源场景2**：吉语佳 — 信用信息修复（Why追问不足）

| 项目 | 详情 |
|------|------|
| **错误** | 看到"电子营业执照"就停止追问，没有质疑"数字证书为何需要纸质授权书" |
| **根因** | 被专业术语迷惑——"电子营业执照"听起来很官方 |
| **后果** | 整条因果链断裂 |
| **融入规则** | "电子流程+纸质材料"必须追问平台截图 |

**综合判断标准**：
- "电子流程+纸质材料" → 必须读附件确认平台是否确实要求纸质
- "平台入驻" → 必须读附件确认平台后台的强制要求
- "仲裁/诉讼" → 必须读附件确认仲裁委/法院出具的正式文件
- 任何有附件的申请 → 附件内容必须作为证据链判断的核心依据

**融入规则**：SKILL.md 步骤3（附件读取前置）+ 步骤4-证据链核实

### 【P4】Why不明时流向/用途无法判断 —— Why是逻辑基础

**起源场景**：吉语佳 — 批量更新六个主体印章（流向/用途混淆）

| 项目 | 详情 |
|------|------|
| **错误** | 流向填"印章店"（这是用途），用途填"广州"（太宽泛） |
| **根因** | 未追问Why——没搞清楚"为什么要更新" |
| **后果** | 流向和用途的逻辑基础不成立，判断全错 |
| **判断标准** | 如果Why没搞清楚，流向填的是办理地点或中间机构而非真正要求方，用途填的是公司所在地或默认地点而非真实使用场景。 |
| **修正方式** | 先追问Why（为什么更新？谁要求更新？在哪里使用？），再确定流向和用途。 |
| **融入规则** | SKILL.md 步骤4-逻辑穿透 |

### 【P5】硬性规则：授权类资质必须有双章合同 —— 授权书不能替代合同

**起源场景**：品牌授权书申请中频繁出现单章授权书

| 项目 | 详情 |
|------|------|
| **错误** | 仅凭"有品牌授权书"就判断What正确，未检查是否有经法务审核的双章合作合同 |
| **根因** | 混淆了"授权书"和"合同"的法律效力 |
| **后果** | 授权链不完整，被授权方无法证明合法经营权 |
| **判断标准** | 授权类资质必须有经法务审核+盖双方合同章的合作合同。**授权书本身不能证明合作关系**，只能证明授权事实。 |
| **修正方式** | 读取附件时，必须同时检查：①授权书 ②合作合同（双章）。缺任意一个都是What不完整。 |
| **融入规则** | SKILL.md 步骤4-证据链核实 |

### 【P6】表单未披露原因→Why就不充分 —— 不能假装知道 + 必须追问案由

**起源场景**：胡涵冰 — 仲裁授权未披露案由

| 项目 | 详情 |
|------|------|
| **错误** | 表单只写"仲裁授权-钟潆娴、龚祁（各2份）"，未披露仲裁原因 → Why输出"应诉/仲裁场景，法人资质为法律程序必需" → 模板化表述，没有追问具体案由 |
| **根因** | analyzeWhy() 仅按关键词匹配输出固定句子，未深入解析事由 |
| **后果** | 未追问案由→无法评估风险；未推导缺席后果→无法让审批人理解紧迫性 |
| **判断标准** | 仲裁/诉讼类必须：①提取被授权人/当事人 ②追问具体案由（劳动纠纷/合同纠纷/竞业/货款等）③如果案由未披露→明确标注"未披露" ④推导缺席后果链 |
| **修正方式** | Why必须包含："被授权人=XXX，⚠️ 【P6】具体仲裁案由未披露，建议补充仲裁申请书" + 缺席后果链（缺席判决→自动败诉→经济赔偿/恢复劳动关系） |
| **融入规则** | SKILL.md 步骤4-逻辑穿透-看背景 |

### 【P7】批量异常模式 —— 同一申请人连续≥3条类似申请需排查系统性原因

**起源场景**：胡涵冰连续3条仲裁申请

| 项目 | 详情 |
|------|------|
| **错误** | 分别审核3条仲裁申请，没有关联分析 |
| **根因** | 未识别批量模式，未追问"为什么这个人连续提交3条仲裁" |
| **后果** | 可能错过系统性用工风险信号 |
| **判断标准** | 同一申请人连续≥3条类似申请（同类型资质/同一场景），Why要排查系统性原因。 |
| **追问方向** | ①到期/损坏/更名/合并？（合理批量）②用工风险信号？（如多人同时仲裁=系统性劳动纠纷）③业务扩张导致？（如批量开店入驻） |
| **附件结合** | 对比多条附件，确认是否同一原因导致。 |
| **融入规则** | SKILL.md 步骤4-逻辑穿透 |

### 【P8】有疑问先检索内部信息 —— 不要质疑已知的内部关系

**起源场景**：质疑"凡岛投资"是否为凡岛主体

| 项目 | 详情 |
|------|------|
| **错误** | 对"凡岛投资"产生疑问，但未先检索内部信息就质疑其关联性 |
| **根因** | 不了解内部组织架构 |
| **后果** | 可能在流向判断中错误地将内部关联公司标记为外部机构 |
| **判断标准** | 凡岛投资=凡岛主体之一。遇到陌生公司名称时，先检查是否为内部关联公司，不要直接质疑。 |
| **融入规则** | SKILL.md 步骤4-逻辑穿透-看流向 |

### 【P9】发现错误立即修正 —— 追加修正版评论

**起源场景**：修正版评论沦为附件复述（无判断价值）

| 项目 | 详情 |
|------|------|
| **错误** | 追加"修正版"时，只机械粘贴附件内容，完全没有三阶段判断 |
| **根因** | 修正脚本设计缺陷——把"读取附件"和"分析判断"拆成两步 |
| **后果** | 评论变成"附件翻译器"，没有提供任何审核判断 |
| **判断标准** | 修正版=完整重新审核，必须包含基于附件的新判断，不是机械复述。 |
| **修正方式** | 修正版必须：①说明修正原因 ②列出附件读取结果 ③重新进行三阶段分析 ④给出新结论。 |
| **融入规则** | SKILL.md 步骤6-修正版 |

### 【P10】分析一致性 —— 绝对禁止简化版替代完整版（新增 v2.1）

**起源场景**：5条审批出现评论冲突

| 项目 | 详情 |
|------|------|
| **错误** | 同一审批实例有2-3条AI评论，结论互相冲突（第一次说"✅通过"，第二次说"❌退回"） |
| **根因** | 第一次用完整三阶段分析，第二次用简化版/快速规则（临时脚本），两套逻辑标准不同 |
| **后果** | 审批人困惑：同一个AI，两次说的不一样 |
| **判断标准** | 同一审批实例的所有评论必须使用**同一套完整三阶段分析逻辑**，绝对禁止用简化版/快速规则替代。 |
| **修正方式** | 追加"统一版"评论，说明冲突原因，基于完整分析重新确认。 |
| **融入规则** | SKILL.md 步骤6-统一版 + 附录A-分析一致性保障 |

### 【节点识别】审核 bot 只处理「审批」节点，「是否领取」等下游节点必须跳过（2026-07-01）

**起源场景**：刘静依 E66C——生产缓存记 `CLOSED/approve`，可 `list` 又把它捞回来当"待审核"，看似"缓存漂移"。

| 项目 | 详情 |
|------|------|
| **真根因** | 审批流有**两个节点**：「审批」(资质审核) + 「是否领取」(总经办领取)。审核早通过了，实例仍 PENDING 是因为**领取节点没点**。`approval tasks query` 把**两个节点的 task 一起吐回**；`list` 只认 `instance_code`、不认节点 → 把「领取」待办当资质审核件。 |
| **生产为何没炸(碰巧)** | 缓存里该 case=CLOSED，list 撞见就跳过——是"被缓存挡住"，不是会分辨。**缓存一旦缺失(隔离测试/换机/迁移/人审未走 bot 记账)→ 领取 task 无人挡 → 重审已通过件**。 |
| **修正** | `case`/`list` 认节点：从 `inst.data.tasks` 取 pending 节点，若无一个匹配审核模式(`QUAL_AUDIT_NODE_RE` 默认 `审批\|审核`)→ `should_skip=true`。`case` 下附件前就 gate；日期窗扫描顺手过滤。fail-safe：读不到 tasks 不跳(宁多审不漏审)。 |
| **可泛化** | "缓存 CLOSED 但飞书仍 PENDING" 不一定是 approve 没生效——**先查 `instances get` 的 `status` 与 `tasks[].node_name/status`**，分清"审批空转"vs"下游节点未完成"。approve 是跨系统三步非原子写(评论→审批动作→缓存CLOSED)，写 CLOSED 前应回读飞书是否真到 APPROVED，否则漂移。 |
| **融入规则** | audit-tool `pendingNodeInfo` + `cmdCase` gate + `applyDateWindow` 过滤 |

### 【卡片折叠/乱序】多条卡片全挤一起 + #N 乱序（2026-07-01，详见 card-generation-pitfalls.md）

| 项目 | 详情 |
|------|------|
| **症状** | 飞书卡片多条 case 全挤在一个块里(`#1 2 3`、多姓名/资质拼一行、多段分析首尾相接)；且 `#N` 每轮乱序 |
| **根因1(折叠)** | PS5.1 `@(管道 \| ConvertFrom-Json)` 把 JSON 数组当**1 个**管道对象包住 → 多条折叠成 1(单条侥幸正常)。修：先落变量再 `@()` |
| **根因2(乱序)** | 并行子代理 write-result → `n` 按完成竞态分配。修：发卡前 `renumberReportByWaitTime` 按 createTime 重排(等待最久=#1)，同步报告+pending_actions |
| **教训** | **多条渲染异常，第一步读真实卡片 JSON(`C:\claude\_card_from_json.json`)，别凭描述猜**——2026-07-01 凭描述连误诊三次("太长""顺序乱")才发现真凶 |
