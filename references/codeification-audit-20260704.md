# 确定性规则 · 代码化盘点（知识库「必须」层 × deterministic-checker 现状）

> 来源：飞书「ai审核知识库」(docx FekFdcj1Eo8EMTxjsw1ct2Aun4e) 的"必须/强制/禁止"确定性规则，
> 逐条对照 `lib/deterministic-checker.js`（R01–R11 + 内部授权 autoApprove）与 references 文字规范。
> 目的：确定哪些确定性规则**已是代码硬闸（每次必跑）**、哪些**只在文字里/完全缺失**（靠 agent 自觉→不可靠）。
> 结论：知识库确定性规则约 ⅔ 未代码化，是"识别执行脱节"的结构性根源。

## 图例
- ✅ 已代码化（R0x / autoApprove）：每次必跑，可靠触发
- 🟡 半代码化：代码只覆盖一部分/仅 CONFIRM 提醒，硬判仍靠 agent
- ❌ 未代码化：只在文字规范里或完全没有 → 靠 agent 记住才触发（今天多次漏的就是这类）

## 汇总：优先代码化清单（❌ 类里最该先做）
1. **申请资质↔本体附件缺件闸**（品牌授权书/商标授权书本体必传、法人对外办理业务申请书必传、诉讼材料/仲裁申请书必传）——一族"申请了 X 必须传 X 的证据"的缺件硬闸，**覆盖今天朱嘉仪+侯成宇两类漏检**。
2. **平台账号绑定：手机号查库 + 实名人职务查干部名单**——两个可机械比对的硬闸。
3. **授权书数值边界**：授权≤3年、授权日期≤合同期限、门店数≤合同——可比对的硬闸。
4. **主体+USCC 一致性**：主体名 vs entities.json 比对。
5. 补全 risk_levels 全资质键；确保 isInternalEntity 覆盖全主体 + **部门层**（研究院/各模块，需从组织架构图同步，见下）。

## 数据缺口
- `entities.json` 只有 **11 个主体**，**无"部门层"**（凡岛研究院、投资模块等）。知识库"主体认知库"指向组织架构图 docx `YM8idX3lxoxXyWxQd9cc79Mdnre` + "凡岛部门和部门负责人"（CEO/法人=黎文祥）。→ 需把部门层同步进 entities.json，否则"研究院/模块是内部部门"这类判断无数据支撑（杜益案根因之一）。
